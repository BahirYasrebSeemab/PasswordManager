# Vault CRUD Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement the full CRUD API for encrypted vault entries in `apps/api` — create, list, get one, update, delete — all owned per-user and gated behind the existing JWT auth dependency.

**Architecture:** New `app/vault/` feature module mirrors the existing `app/auth/` module's shape (`models.py`, `schemas.py`, `router.py`). One new table (`vault_entries`, FK to `users.id`). Every route depends on `get_current_user` (already built in the auth feature) and every lookup is a single query that filters by both `id` and `user_id` together, so "not yours" and "doesn't exist" are indistinguishable to the caller.

**Tech Stack:** FastAPI, SQLAlchemy 2.0 (`select()`/`scalars()`), Alembic, Pydantic v2, pytest + `httpx`/`TestClient`, PostgreSQL.

**Spec:** `docs/superpowers/specs/2026-09-05-vault-crud-design.md`

## Global Constraints

- Every vault route requires `Depends(get_current_user)` — there is no unauthenticated way to touch vault data.
- Ownership is enforced by a single query condition: `WHERE id = :id AND user_id = :current_user_id`. Never split this into "look up the row" then "check ownership" as two steps.
- A vault entry that doesn't exist and a vault entry that exists but belongs to someone else return the **identical** `404` — never `403` for the second case. This mirrors the auth feature's enumeration-avoidance principle.
- `ciphertext` is stored as `Text` (unbounded), never a capped `String(N)` — the server treats it as opaque and enforces no length limit.
- `GET /vault` returns the full list, unpaginated (YAGNI — personal-scale vault).
- `PUT /vault/{id}` is a full replace only — there is no partial-update endpoint.
- `user_id` on `vault_entries` is indexed, since every query in this feature filters by it.
- The user runs every `git commit` themselves — every task ends by telling the user what to stage and commit, never by an agent running git.
- The user runs all Alembic/package commands themselves — tasks that need a migration tell the user the exact command to run and wait for their confirmation before the next task assumes the table exists.

```python
from datetime import datetime

from pydantic import BaseModel, field_validator


class VaultEntryCreate(BaseModel):
    ciphertext: str

    @field_validator("ciphertext")
    @classmethod
    def not_empty(cls, value: str) -> str:
        if not value.strip():
            raise ValueError("ciphertext must not be empty")
        return value


class VaultEntryUpdate(VaultEntryCreate):
    pass


class VaultEntryResponse(BaseModel):
    model_config = {"from_attributes": True}

    id: int
    ciphertext: str
    created_at: datetime
    updated_at: datetime
```

`VaultEntryUpdate` inherits `VaultEntryCreate` rather than duplicating the validator — same pattern as `RegisterRequest`/`LoginRequest` sharing `AuthCredentials` in the auth feature. It's kept as its own class (not just an alias) in case create/update validation ever needs to diverge later.

```python
from fastapi import APIRouter, Depends, status
from sqlalchemy import select
from sqlalchemy.orm import Session

from app.auth.dependencies import get_current_user
from app.auth.models import User
from app.db.session import get_db
from app.vault.models import VaultEntry
from app.vault.schemas import VaultEntryCreate, VaultEntryResponse

router = APIRouter(prefix="/vault", tags=["vault"])


@router.post("", response_model=VaultEntryResponse, status_code=status.HTTP_201_CREATED)
def create_vault_entry(
    payload: VaultEntryCreate,
    current_user: User = Depends(get_current_user),
    db: Session = Depends(get_db),
) -> VaultEntry:
    entry = VaultEntry(user_id=current_user.id, ciphertext=payload.ciphertext)
    db.add(entry)
    db.commit()
    db.refresh(entry)
    return entry


@router.get("", response_model=list[VaultEntryResponse])
def list_vault_entries(
    current_user: User = Depends(get_current_user),
    db: Session = Depends(get_db),
) -> list[VaultEntry]:
    entries = db.scalars(
        select(VaultEntry).where(VaultEntry.user_id == current_user.id).order_by(VaultEntry.created_at.desc())
    ).all()
    return list(entries)
```

```python
def _get_owned_entry(entry_id: int, current_user: User, db: Session) -> VaultEntry:
    entry = db.scalars(
        select(VaultEntry).where(VaultEntry.id == entry_id, VaultEntry.user_id == current_user.id)
    ).first()
    if entry is None:
        raise HTTPException(status_code=status.HTTP_404_NOT_FOUND, detail="Vault entry not found")
    return entry

    db: Session = Depends(get_db),
) -> VaultEntry:
```

Update the top-of-file import line `from fastapi import APIRouter, Depends, status` to also include `HTTPException`, so it reads `from fastapi import APIRouter, Depends, HTTPException, status`.

**Why one query instead of two:** it would be tempting to write `entry = db.get(VaultEntry, entry_id)` (look it up by ID alone), then `if entry.user_id != current_user.id: raise 404`. That's two logical steps, and it's exactly the shape of code where a future edit — adding a caching layer, an early return, a refactor — can accidentally keep the first step and lose the second, silently turning this into "any authenticated user can read any entry by ID." Folding both conditions into one `WHERE` clause makes that mistake structurally impossible: there is no code path that returns a row without both conditions already having been true in the database engine itself, before any Python code ran.
